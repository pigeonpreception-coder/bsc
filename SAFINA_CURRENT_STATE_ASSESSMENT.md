## 1. Executive Summary

Safina is a **working, single-region, multi-tenant SaaS application** for Balanced Scorecard–based strategic management: an organization's admin sets up mission/vision/values, generates an AI-assisted strategic plan and a cascading Balanced Scorecard, staff update their KPI actuals, and the system computes RAG status, weighted performance scores, and exports the finished plan as Word/PDF. It is built on Next.js 16 (Server Actions, not a REST API) and Supabase (Postgres + Auth + Storage), deployed to Vercel with three scheduled cron jobs.

**What it solves today:** a small-to-mid-size organization can go from "we have no formal strategic plan" to a generated, editable, cascaded Balanced Scorecard with live KPI tracking and a board-ready exported document — without needing a consultant to build the template by hand. That core loop is real and functionally complete.

**What's changed since the original baseline:** six fresh gap-scan passes have now run (§14, §15, §16, §18, §19) and found and closed 28 issues between them — four cross-tenant write gaps, one cross-tenant document-confidentiality read, one cross-tenant account-existence leak, an open redirect on the auth callback route, an SSRF hole in the AI website-context feature, unenforced upload/payload size limits, a decompression-bomb exposure in `.pptx` parsing, no rate limiting on password-reset or AI-generation requests, unset `secure` on session cookies, no session revocation on password change, a privileged action trusting a caller-supplied token, and several other silent-failure and defense-in-depth gaps; automated SAST (GitHub CodeQL, `security-extended` query suite), dependency scanning (Dependabot), and secrets scanning (gitleaks, full git history) now run in CI on every push/PR plus weekly (§17) — passes 5 and 6 both confirmed this tooling and manual review are complementary, not substitutes: neither pass found anything CodeQL/Dependabot/gitleaks would have caught; an automated test suite (112 tests) and a CI pipeline now exist; the "admin types your password" invite anti-pattern is gone, replaced with a real email-invite flow; login has rate limiting; the tenant-isolation gap in the corporate-BSC data helper is closed; audit logging now covers team invites, org-hierarchy saves, and document exports in addition to scorecard edits and tenant/license admin actions; cascade weighting is configurable via a settings screen instead of a silent hardcoded default; the duplicated `department` field across `org_positions` and `users` is consolidated to one source of truth; the unguarded org-hierarchy recursion that risked crashing the nightly performance-recalc job on corrupted data is fixed; the duplicated invite/account-creation logic is consolidated into one helper; the Super Admin tenant list is paginated instead of silently capped by PostgREST's default row limit; all three cron jobs process tenants with bounded concurrency instead of a fully serial loop; Sentry error monitoring is wired into the server, edge, and client runtimes plus a root-level error boundary; a notification system (header bell + email via Resend) now exists, distinct from the older page-scoped KPI alerts panel, and covers four events: position assignment, weekly-advisory generation, new-account welcome, and strategic-plan approval.

**One caveat on the Sentry item:** the monitoring code is complete and inert-safe (it does nothing until a DSN is configured), but it requires a manual step outside this repository — creating a Sentry project and setting `NEXT_PUBLIC_SENTRY_DSN` — that could not be verified from here. Whether it is actually receiving events in production is unconfirmed. Source-map upload (needed for readable, non-minified stack traces) was also deliberately not wired up — see §3.

**The same caveat applies to email notifications:** the code path is complete and inert-safe (no-ops until `RESEND_API_KEY` is set), but whether the account/API key is actually configured in production, and whether real emails are landing (not caught by spam filters, domain verified, etc.), is unverified from here.

**TOTP-based MFA now exists** (§22) — self-service enrollment for every role at `/account`, a login-time challenge enforced in middleware, and mandatory enrollment before dashboard/admin access for `company_admin`/`super_admin`. Code-complete and unit-tested, but **not yet manually verified end-to-end with a real authenticator app** — same caveat category as Sentry/Resend above: the code path exists, but "exists" and "confirmed working against a live authenticator app" are different claims, and only the second one is what actually protects an account.

**What still prevents it from being a production-grade enterprise platform:** SSO, fine-grained RBAC beyond today's five fixed roles, and no billing integration behind the "license" concept. These remain real gaps — none of the fixes above touched them. MFA, the fourth item previously in this list, is addressed as of §22.

**What prevents it from being a global platform:** no i18n/locale infrastructure, no multi-currency, no data-residency controls, single shared Postgres instance with no sharding/read-replica strategy, no multi-region deployment. None of this is implemented, and none of it needs to be yet — it isn't serving customers who require it.

## 3. Current Architecture

**Frontend:** Next.js 16.2.10 App Router, React 19.2.4, Server Components + Server Actions (no separate REST API for app logic — only 4 `route.ts` handlers exist, 3 of which are cron endpoints). Tailwind CSS 4. Charts via `recharts`.

**Backend:** No separate backend service — all business logic lives in Server Actions co-located with the routes that use them. Authorization is still inline `if (user.role !== ...)` conditionals rather than a centralized policy layer — that architectural choice is unchanged, though the duplicated invite/account-creation logic within it is now consolidated (`src/lib/user-invite.ts`).

**Database:** Single shared Postgres instance (Supabase), 26 tables across 19 sequential migrations (`login_attempts` and `notifications` added, `user_permissions` dropped, this session), shared-schema multi-tenancy via `tenant_id` + Row-Level Security on every tenant-scoped table. Every FK and `tenant_id` column is indexed.

**Auth:** Supabase Auth, email/password only. Two client tiers: an RLS-scoped client for normal use, and a `server-only` service-role client (`src/lib/supabase/admin.ts`) that bypasses RLS. The one place that previously trusted a caller to have pre-scoped by tenant (`getCorporateBscView`) now asserts `tenantId` internally. Login now has Postgres-backed rate limiting (`src/lib/rate-limit.ts`) — 5 attempts/15min per email, 20/15min per IP.

**Storage:** One private Supabase Storage bucket (`company-documents`), tenant-isolated by folder-prefix RLS policy for direct client uploads. **Fixed** — the one server-side read path that used the RLS-bypassing admin client (`buildUploadedDocumentContext`, feeding AI document generation) didn't re-check that path against the caller's tenant; it now does (`isPathOwnedByTenant()`, §15). **Fixed** — the bucket itself had no `file_size_limit`/`allowed_mime_types` (migration `0020`), so the client-side 20MB/extension checks were the only enforcement; both are now set server-side, and the `.pptx` text extractor has a decompressed-size ceiling against a crafted zip-bomb upload (§16).

**AI:** Anthropic SDK (`claude-sonnet-5`), used with forced tool-calling (structured JSON output, not free text) for scorecard generation, theme generation, and document-section generation. Logged to an `ai_sessions` table.

**Infrastructure:** Vercel deployment, 3 scheduled cron jobs (`daily-tasks`, `performance-recalc`, `weekly-advisory`). **Fixed** — each now processes tenants with bounded concurrency (`src/lib/concurrency.ts`, a worker-pool capped at 5 concurrent tenants) instead of a fully serial loop; positions within a tenant still process sequentially by design, to keep total concurrent AI-API calls predictable. No region pinning, no CDN configuration beyond Vercel defaults, no containers/Kubernetes. `maxDuration` is still not set on the cron routes — the achievable value depends on the Vercel plan tier, which couldn't be determined from the repository.

**DevOps:** **Fixed** — a CI pipeline now exists (`.github/workflows/ci.yml`: typecheck + lint + tests on every PR and push to `main`), and an automated test suite exists (Vitest, 112 tests across 19 files covering the scoring/cascade engine, tenant isolation, cron auth, rate limiting, the shared invite helper, audit logging, plan-period math, storage-path/IP ownership guards, redirect-path validation, HTML-escaping, and the notification/email helpers). True RLS/Postgres integration testing remains out of scope — no Supabase CLI/Docker access in this environment to run a local Postgres instance against the real policies; what exists tests the application-layer logic that supplements RLS. **Fixed** — automated SAST now runs in CI (`.github/workflows/codeql.yml`, GitHub CodeQL, `security-extended` query suite, on push/PR to `main` plus a weekly schedule — free for this public repo), dependency/SCA scanning via Dependabot (`.github/dependabot.yml`, weekly, npm + GitHub Actions), and secrets scanning via gitleaks (`.github/workflows/gitleaks.yml`, scans full git history, not just the current tree) — see §17. DAST deliberately not added yet: no staging URL exists to scan, and most of the app sits behind auth, so a scan against an unauthenticated instance would have limited value. Secrets via `process.env`, no secrets manager beyond Vercel's own env-var store — gitleaks is now the backstop against one accidentally landing in a commit anyway.

**Integrations:** Anthropic (AI), Supabase (DB/Auth/Storage). **Fixed** — Sentry (`@sentry/nextjs`) is now wired for error monitoring: server/edge init and the `onRequestError` hook in `src/instrumentation.ts`, client init in `src/instrumentation-client.ts`, plus a root-level `global-error.tsx` boundary. Gated on `NEXT_PUBLIC_SENTRY_DSN` and inert without it — **whether it's actually configured and receiving events in production is unverified from this repository**. Source-map upload (`withSentryConfig` in `next.config.ts`, needed for readable production stack traces) was deliberately not added — it requires `SENTRY_AUTH_TOKEN` plus org/project config, and this environment's own `next build` already fails on an unrelated Windows path-length issue in the nested worktree directory, so a build-plugin change couldn't be verified safe against the Turbopack build. **Fixed** — Resend (`resend` package) is now wired for transactional email (`src/lib/email.ts`), gated on `RESEND_API_KEY` and inert without it, same operational-verification caveat as Sentry. Still no payment/billing provider, no SMS provider, no CRM/ERP/accounting integration, no identity provider (no SSO/SAML/OIDC beyond Supabase's own auth).

## 4. Multi-Tenancy Assessment

Real, not cosmetic: every tenant-scoped table has RLS enabled with a `tenant_id = current_tenant_id() OR is_super_admin()` policy. Storage follows the same pattern via folder-prefix policy. This is a **shared-database, shared-schema** model — one Postgres instance, tenant isolation entirely at the row level, no per-tenant schema/database, no tenant-selectable data residency.

**Can it scale to thousands of organizations?** Plausibly, for the database layer itself — Postgres with proper indexing handles millions of rows fine. **The cron scaling ceiling identified in the original baseline is improved, not eliminated.** All three scheduled jobs now process up to 5 tenants concurrently instead of one at a time, which meaningfully pushes out the point at which tenant count causes a function-timeout failure — but it doesn't remove the ceiling. A true fix (a real job queue, or per-tenant fan-out invocations) would require new infrastructure and was deliberately not built speculatively, consistent with this document's own recommendation not to over-build ahead of an actual scale signal.

**To millions of organizations:** would still require a fundamentally different tenancy/infrastructure model. Not a near-term concern given current usage.

## 16. Fourth Gap-Scan Pass

Run on explicit request, after §15's findings were fully closed. Same method, extended: the agent was told not to re-flag anything in §5/§6/§9/§14/§15 and pointed at five specific new angles — file-upload path traversal, prompt-injection risk from AI-fed uploaded/website content, rate limiting beyond login, an exhaustive sweep of every `createAdminClient()` call site for unscoped queries, and remaining test-coverage gaps. All 6 findings were fixed; none were deferred.

| Finding | Fix |
|---|---|
| `/auth/callback` (`route.ts`) built its post-login redirect as `` `${origin}${next}` `` with `next` read straight from the query string and never validated. A payload like `next=@evil.com/phish` parses in every browser as host `evil.com` (userinfo splice) — an open redirect served from the real auth domain, the strongest possible pretext for a phishing link. This is the most severe finding of this pass: unlike every prior finding (all cross-tenant *data* bugs), this is a bug that can be weaponized against a human, not just against the data model. | New `isSafeRedirectPath()` requires a single leading `/` with no second `/` or `\` immediately after (blocks the userinfo-splice payload, `//evil.com`, and the `/\evil.com` browser-parsing variant of the same bypass); anything that fails it falls back to `/`. Each pass's scope was written specifically to catch what the previous passes might have missed, and each one still found something outside its predecessors' framing. That is the strongest evidence in this document that a fifth pass would find a fifth category, not that the codebase has run out of categories.

## 21. Eighth Gap-Scan Pass — Cron Jobs Silently Redirected to /login, Never Actually Running

Run on explicit request, immediately after §20. Same method, but this time the subagent was pointed at genuinely fresh angles not yet swept in any prior pass: storage/signed-URL scoping, webhook/callback signature verification, a super-admin-specific role-gate sweep, client-side-only-state-change protections (distinct from the notification-replay class fixed in §20), timing-safe comparisons beyond the ones already fixed, user-supplied file-path/dynamic-import construction, unbounded-loop/DoS surfaces, and security headers. Most of these came back clean — signed URLs are tenant-scoped, no webhook endpoints exist, role gates are all correct, no new timing or path-construction issues found. One finding did surface, and it's the most operationally significant one of the last several passes: **the three scheduled cron jobs, and `/api/sentry-check`, likely never actually run in production.**

| Finding | Fix |
|---|---|
| `middleware.ts`'s matcher (`"/((?!_next/static\|_next/image\|favicon.ico\|.*\\.(?:svg\|png\|jpg\|jpeg\|gif\|webp)$).*)"`) runs the Supabase session check against every route, including `/api/**` — it excludes only static assets, not API routes. `updateSession()`'s `PUBLIC_PATHS` (`src/lib/supabase/middleware.ts`) previously listed only `["/login", "/auth"]`. Vercel Cron's scheduled invocations (per `vercel.json`, driving `/api/cron/daily-tasks`, `/api/cron/performance-recalc`, `/api/cron/weekly-advisory`) and any plain visit to `/api/sentry-check` carry **no Supabase session cookie** — they authenticate via `Authorization: Bearer $CRON_SECRET` (or `?secret=`) checked *inside* each route handler. With no session cookie, `supabase.auth.getUser()` resolves to `null`, `isPublicPath` was `false` for every `/api/*` path, and the middleware fired its `NextResponse.redirect("/login")` branch before the request ever reached the route handler's own auth check. Concrete effect: the nightly performance-recalc snapshot, the daily AI task generation, and the weekly advisory generation — every scheduled background job the app has — would receive a 307 to `/login` instead of executing, silently, with nothing in normal monitoring flagging a redirect as a failure. The route-level `CRON_SECRET` hardening from task #1 (the very first fix of this whole session) was unreachable dead code from the one caller — Vercel's scheduler — that actually needed it. Verified by reading the full chain end-to-end: `middleware.ts` matcher → `PUBLIC_PATHS` check → redirect branch → each cron route's `isValidCronRequest()`/`/api/sentry-check`'s own secret check, none of which is reachable first. Confirmed via `grep` that no `/api/*` route depends on the session cookie for its own auth (all four use their own independent secret check), so exempting the whole prefix has no auth-bypass side effect. | Added `"/api"` to `PUBLIC_PATHS` in `src/lib/supabase/middleware.ts`, exempting every `/api/*` route from the cookie-session redirect gate — each already authenticates itself independently. Extracted the path-matching logic into an exported pure function `isPublicPath(pathname)` (previously an inline `.some()` in `updateSession`) so it has direct unit-test coverage, matching this session's established pattern of pulling testable logic out of request/DB-coupled code. New `src/lib/supabase/middleware.test.ts` covers all three cron paths, `/api/sentry-check`, `/login`, `/auth/callback`, and confirms `/dashboard` and `/` remain protected. |

**No other new findings met the bar this pass.** Storage/signed-URL scoping (`export-actions.ts`), super-admin action gates (`admin/actions.ts`), and Puppeteer-based PDF rendering (`plan-document-html.ts` — no external resource references, so no SSRF-via-render variant) were all checked directly and found consistent with what prior passes already established or fixed.

**Fourth data point — and the most consequential one yet.** Unlike passes 5–7, this finding isn't a hardening gap or a defense-in-depth improvement — it's a plain correctness bug that, if genuinely reaching production this way, meant the app's entire background-job subsystem has been non-functional since it was built, with no error surfacing anywhere a human would notice (a 307 redirect looks like ordinary traffic in most logs, not a crash). It's also a variant of this session's recurring meta-finding from §19/§20: the very `CRON_SECRET` mechanism built in task #1 to secure these routes was never actually exercised by its real caller, because a completely separate layer (middleware, added later, for an unrelated reason — gating the dashboard behind login) silently intercepted the request first. Two independently-correct pieces of security code (the cron-secret check, the session-redirect gate) composed into a broken system. Worth flagging for the user directly: **it would be worth manually confirming in the Vercel dashboard that these three cron jobs have actually been running on schedule** — if this bug has been live since the cron routes were first deployed, there may be a backlog of missed daily-task generation, performance recalculation, and weekly advisory runs to consider backfilling.

Traced `_unenroll` in `node_modules/@supabase/auth-js/dist/module/GoTrueClient.js:4667-4679`: it issues a `DELETE /factors/:id` and returns — unlike `_verify` (used by the login challenge and enrollment), it never calls `_saveSession()`, so the browser's session cookie keeps its stale `aal2` JWT claim and cached factor list. ## 24. Tenth Gap-Scan Pass — Untrusted Origin Header in Auth Emails, a False UI Claim

Run on explicit request, immediately after §23. Pointed at fresh territory not yet swept in any prior pass — the `resetUserMfaFactors` recovery-path UI, the onboarding-vs-mandatory-MFA redirect interaction, upload-path re-verification, a fresh read of the `/account` UI files, and a dependency check. Most of that came back clean (see below). Two findings, both verified independently before fixing — one by reading Next.js 16.2.10's actual bundled CSRF-check source to confirm exactly what it does and doesn't protect against, the other by grepping the full codebase for every session-revocation call site to confirm the claim was actually false, not just unverified.

| Finding | Fix |
|---|---|
| **Most severe finding across all ten passes.** `requestPasswordReset` (`src/app/auth/forgot-password/actions.ts`) — an **unauthenticated** action — built the password-reset email's link from `headers().get("origin")`, the raw client-supplied `Origin` header, with no validation. Traced Next 16.2.10's actual CSRF check (`node_modules/next/dist/server/app-render/action-handler.js`) to confirm what it protects against: it compares `Origin` against `Host`/`X-Forwarded-Host` — both from the same untrusted request — which stops a *browser* on another origin from forging a same-origin-looking request (the browser itself won't let a script set a mismatched `Origin`). It does nothing to stop a direct, non-browser client (curl, a script) from sending a request with a self-consistent but entirely fake `Host`+`Origin` pair. If that reaches the app (dependent on Vercel's edge routing for a mismatched `Host` — an infra fact outside this repo, not fully verifiable from source, hence not "confirmed" exploitable end-to-end) and Supabase's own redirect-URL allow-list doesn't block it (also project config outside this repo), an attacker could get a real, correctly-branded password-reset email sent to any victim's real inbox with its link pointing at an attacker-controlled domain — a phishing-to-account-takeover chain, using this app's own sending reputation. Two lower-severity variants of the identical pattern also existed in `src/app/dashboard/team/actions.ts` and `src/app/admin/actions.ts` (both feed `src/lib/user-invite.ts`'s `redirectTo`), but those require an already-authenticated `company_admin`/`super_admin` to trigger — an insider/compromised-account risk, not an anonymous one. | New `src/lib/site-url.ts` exports `resolveAppUrl(requestOrigin?)`, extracted from a private, near-identical helper that already existed in `src/lib/email.ts` (now imports the shared version instead — a duplicate-logic cleanup as a side effect). Prefers `NEXT_PUBLIC_APP_URL`, then `VERCEL_URL` (auto-set on every Vercel deployment, no manual config needed — unlike the Sentry/Resend items, this fix isn't gated on a setup step the user still has to do), and only falls back to the request's own origin if neither is set — i.e. local dev, where there's no real trust boundary being crossed. All three call sites (`forgot-password/actions.ts` directly, `user-invite.ts` internally so its two callers didn't need any change) now route through this instead of trusting the header directly. New tests: `src/lib/site-url.test.ts` (the pure function, all four branches) and two new cases in `src/lib/user-invite.test.ts` confirming the env var wins over a spoofed origin, and that the header is still used as the local-dev fallback. |
| The Account &amp; Security page (`src/app/account/page.tsx`) tells every user "Verifying a new device signs out your other active sessions" — a claim that was **false**. Grepped the whole `src` tree for every call to `signOut(..., "others")` and found exactly one: `revokeOtherSessions()` in `src/app/auth/reset-password/actions.ts`, wired only into the password-reset flow, never into MFA enrollment. A user enrolling MFA specifically because they suspect their account is compromised — arguably the single most likely reason someone reads that sentence and acts on it — would have gotten no such protection: any already-open session (including an attacker's) stayed fully live after verification. | Rather than just correcting the copy, wired the real behavior in: `verifyMfaEnrollment` (`src/app/account/actions.ts`) now calls the same, already-hardened `revokeOtherSessions()` (with its existing caller-ownership check, §19) after a successful `challengeAndVerify()`, using the just-refreshed session's own access token. Best-effort, matching that function's own established pattern — the MFA verification itself has already succeeded by that point, so a failure here shouldn't block the user. The UI's claim is now true instead of false. Three new/updated test cases in `src/app/account/actions.test.ts` cover the call, its argument, and the no-session edge case. |

**Explicitly checked and confirmed clean:** the `ResetMfaButton` client component and its wiring (`userId` is server-fetched and tenant-scoped, not client-editable; the confirm-dialog text matches the real effect); the onboarding-vs-mandatory-MFA redirect interaction (traced a fresh company_admin signup end-to-end — middleware always resolves MFA enrollment before any onboarding page code runs, no loop); `saveBusinessProfileDraft`'s existing 100KB cap (§19) still covers every free-text field, not just the ones originally named; only one upload entry point exists in the whole app, no second unaudited path; `MfaEnrollmentPanel.tsx`'s factor list is recomputed from props on every render, so `router.refresh()` always reflects the current server state, no stale-UI bug; no otpauth/qrcode-style dependency was accidentally added — MFA correctly uses GoTrue's own returned SVG as originally planned; role-escalation, `cascade_weights` tenant-scoping, and `export-actions.ts` signed-URL scoping were all re-checked with no gaps found.

**Ten passes in, still finding real things — and the most severe one yet was hiding in code nine passes old, not the newest feature.** Unlike passes 5–9, which mostly found issues in recently-added code, this pass's most significant finding was in `forgot-password/actions.ts`, present since early in this session and never previously examined from the "what can an anonymous attacker send us" angle. The lesson isn't just "check new code" (§19/§20/§21/§23's recurring point) — it's that a codebase this size still has old, unexamined corners after nine dedicated passes, and the finding rate genuinely has not converged to zero.

## 29. License Entitlement Engine — Seat-Limit Enforcement (Phase 1 of a Multi-Phase Licensing Build)

Requested via a full 35-section commercial-licensing/billing spec (self-service admin signup, license catalog, Stripe-style checkout, payment webhooks, seat enforcement, upgrade/downgrade, admin transfer, org-hierarchy configurability, and 13 acceptance tests). This section is **Phase 1 only**: the License Entitlement Engine and concurrency-safe seat-limit enforcement (spec §5–9, §19, §21, §23, §29–30). Payment/checkout (spec §4, §16–18, §24–26) is deferred to Phase 2, blocked on choosing and configuring a real payment provider (Stripe, per the user's stated preference for when that phase starts) — nothing in this phase depends on that choice.

**What's explicitly deferred, stated plainly rather than silently dropped:** checkout/webhooks/payment-gated activation; a full data-driven pricing catalog (today's fix is a simple per-tenant seat count a `super_admin` sets directly — a real catalog needs real prices to catalog); admin transfer/delegation; configurable org-hierarchy *types* (`org_positions` already supports a hierarchy, just not tenant-configurable structure kinds); email-domain verification; and finer-grained seat-counting categories (invited/pending/active/suspended each counted differently) — Phase 1's policy is the simplest defensible one, stated explicitly: **every row in `public.users` for a tenant consumes a seat**, matching how the app already worked before this pass (an invited-but-unconfirmed user already has a real profile row).

**The core engineering problem, solved correctly:** a naive "check current count, then insert" from application code races under concurrency — the exact gap the spec's own §19/Test 7 calls out, and Supabase's JS client can't run a multi-statement atomic transaction to close it. The fix is a single Postgres function, `provision_tenant_user()` (migration `0023_license_entitlement.sql`), called via `supabase.rpc()`, that does the capacity check **and** the insert inside one transaction while holding a row lock (`for update`) on the tenant. A second concurrent call for the *same* tenant blocks until the first commits, then re-reads the now-current count; different tenants never block each other. This can't be exercised by an automated test in this environment (no live Postgres to fire real concurrent transactions against) — the guarantee is a property of the SQL itself, documented above for review, not asserted by a mocked unit test claiming something it can't actually prove.

**A security control that had to be gotten right, not left to default behavior:** Postgres grants `EXECUTE` on a new function to `PUBLIC` by default. Left as-is, any authenticated (or even anonymous) Supabase client could call `provision_tenant_user` directly via `.rpc()`, bypassing every application-level role gate (`addTeamMember`'s `manager`/`staff`/`viewer`-only restriction, `createCompanyAdmin`'s `super_admin` check) and inserting a `public.users` row for an arbitrary id they don't own. The migration explicitly revokes `EXECUTE` from `public`/`anon`/`authenticated` and grants it only to `service_role` — the role the existing admin client already authenticates as. Worth a dedicated look in a future gap-scan pass regardless, matching this session's established practice for every new trust-sensitive surface.

**What was built:** `tenants.max_users`/`is_unlimited_users` (nullable int + boolean, `check` constraint requiring one or the other). `src/lib/licensing.ts` — `getEntitlement(tenantId)`, the single authoritative read every UI queries (spec §9's "centralized" requirement, satisfied directly rather than re-derived per screen); `canReduceSeatsTo(tenantId, newMax)`, the downgrade guard (spec §25/Test 11) that rejects with the spec's exact wording pattern rather than silently deactivating anyone; `LICENSE_TIER_DEFAULT_SEATS` (`basic: 10, professional: 50, enterprise: unlimited`), a named, clearly-labeled Phase 1 placeholder for what becomes a real pricing catalog once Phase 2 exists — unlimited is a real `is_unlimited_users` boolean (spec §8's explicit ask), never a sentinel number. `inviteUserAccount` (`src/lib/user-invite.ts`, the one shared choke point both `addTeamMember` and `createCompanyAdmin` already funneled through) and `signUpNewTenant` (`src/lib/signup.ts`) both now call `provision_tenant_user` instead of a plain insert; an over-limit attempt surfaces the exact user-facing message spec §7 specifies. `admin/actions.ts` gained `updateTenantSeats` (`super_admin`-gated, audit-logged, downgrade-guarded) and `createTenant` now seeds `max_users`/`is_unlimited_users` from the chosen tier at creation time instead of leaving them unset. New `SeatLimitForm.tsx` on the tenant detail page shows live utilization and lets a `super_admin` edit the entitlement; a new read-only "License & users" card on `/dashboard/settings` shows the same figures to the tenant's own `company_admin`, with no write path exposed to that role at all — satisfying spec §22's "must not bypass licensing restrictions" by construction, not by a runtime check.

**Verified:** `npx tsc --noEmit`, `npm run lint`, `npx vitest run` all clean — 190 tests, 8 net new (`licensing.test.ts` new; `user-invite.test.ts` and `signup.test.ts` rewritten to mock the RPC call, with a new case each for the seat-limit-reached message and rollback). **Not verified:** the migration hasn't been applied to a live Supabase project in this environment (no live credentials) — the `for update` locking behavior, the `EXECUTE` grant/revoke actually taking effect, and the exact error-message plumbing through a real `.rpc()` call all need a manual pass against a live database before this is relied on in production, same caveat category as every other feature built this session without live infrastructure to test against.

**Scope decisions, flagged rather than silently narrowed:**

## 31. Score Approval — Formal Review of Submitted KPI Values (Second of the 11-Part Enterprise Spec)

**Superseded by §33.** The single-level, `company_admin`-only approval described in this section was replaced by a two-level, organizational-hierarchy-resolved approval chain per an explicit follow-up governance spec. Left in place below for its own historical record (the reasoning about *why* a governance layer sits on top of live scoring without gating it still applies), but the authorization model it describes — `company_admin` as sole approver — is no longer how the system behaves. See §33 for the current model.

Second area from the same 11-part spec, picked directly (not asked) since the user delegated the choice: "Formal review/approval of scores or ratings" was flagged **Missing** in §2 — scores were purely computed from actual-vs-target with no manager sign-off step anywhere.

**Why this couldn't be a copy of the existing `approveStrategicPlan()` precedent, confirmed by reading it first:** that function is a single-instance, single-status-field flip (`draft`→`active`) on one row per tenant, broadcasting to the whole tenant, with no audit log call. Score approval is inherently many-rows-by-many-edits, not a singleton — and a closer look at the schema surfaced a real constraint worth naming: **`performance_scores` has no period/quarter concept at all** — it's destroyed and fully reinserted by `calculatePerformanceScores()` on every single "Actual" edit anywhere in the tenant (`src/lib/performance.ts`). Anything attached to that table as "approval state" would be wiped by the very next edit, by anyone, anywhere. `scorecard_rows` — the row that actually holds the submitted value — is the only place approval state can durably live.

**Scope decisions, flagged rather than silently narrowed:**

- **Approval authority is `company_admin` only, not a resolved-from-the-org-chart "direct manager."** The codebase has no existing concept of "my direct reports" for permissioning — `org_positions.reports_to_id` is used today only for score-cascade math and a one-hop "Levels Below" dashboard display, never for authorization; `manager` and `staff` are treated identically everywhere edit rights are checked (`row-actions.ts`'s `canEdit`), and the actual per-row gate is row-ownership (`responsible_person === user.id`), not hierarchy. Building a real "resolve X's approving manager via the org chart" helper — handling unassigned positions, users with no position, and broken/partial chains — is a separate, larger feature with no existing test coverage to build on. `company_admin` already has final edit authority on every field of every row today, so extending that same authority to approval is consistent with the existing boundary, not a new one.
- **A `company_admin`'s own actual-value edit auto-approves rather than entering the same `pending_approval` queue.** They already hold final sign-off authority — routing their own edit through a queue only they can clear is a pointless self-approval loop, not a real control.
- **Approval is a governance/audit trail layered on top of live scoring, not a gate on it.** A `pending_approval` or even `rejected` actual value still feeds `computeAutoStatus`/`calculatePerformanceScores` exactly as before — the RAG status and dashboard scores are not held back pending review. Making unapproved values not count would touch the composite-score engine significantly for a real design question (do rejected values revert to the prior figure? to null? stay visible-but-excluded?) that the spec item as flagged doesn't resolve, and risked a much larger, riskier change than "formal review" strictly requires. Stated here explicitly rather than discovered as a gap later.
- **No revert-on-reject.** Rejecting a submission flags it (`rejection_reason`, notification to the submitter) but does not roll the value back to the prior `performance_snapshots` entry — the existing snapshot history already gives a `company_admin` the prior figure to reference manually if they want the submitter to re-enter it. An automatic revert was considered and deferred as unnecessary complexity for a first version.

**What was built:** `supabase/migrations/0025_score_approval.sql` adds `scorecard_rows.approval_status` (`pending_approval`/`approved`/`rejected`, checked, default `'approved'` — so existing rows and rows with no actual yet never appear to need review), `approved_by`, `approved_at`, `rejection_reason`, plus a partial index on `(tenant_id) where approval_status = 'pending_approval'` for the review-queue query. `row-actions.ts`'s existing `updateScorecardRow()` — the single confirmed write path for `scorecard_rows.actual` (verified with a repo-wide grep; no cron, AI-generation, or bulk-import path writes it) — now sets `approval_status` on every `actual` edit per the rules above, and notifies every `company_admin` in the tenant (`score_pending_review`, bounded-concurrency broadcast mirroring `approveStrategicPlan()`'s pattern) when a manager/staff submission needs review. A new `approveScorecardRow(rowId, decision, reason?)` action (`company_admin`-gated, idempotent no-op on an already-decided row, rejects a `rejected` decision with no reason) records the decision, audit-logs it (`approve_score`/`reject_score` — a real gap `approveStrategicPlan()` itself still has, noted for a future look), and notifies the submitter (`score_approved`/`score_rejected`, respecting their own email-notification preference — unlike account-status-change notifications, a score decision isn't a security event). A new `/dashboard/approvals` page (new nav link, `company_admin`-only) lists every pending row tenant-wide with Approve/Reject controls (`ApprovalControls.tsx`, a reject requires typing a reason first); `ScorecardTable.tsx`/`EditableCell.tsx` also gained an inline `ApprovalBadge` next to the Actual cell itself, so "pending review" or "rejected: reason" is visible without leaving the scorecard.

**Verified:** `npx tsc --noEmit`, `npm run lint`, `npx vitest run` all clean — 222 tests, 9 net new (`row-actions.test.ts`, new — this "use server" file had zero prior test coverage of any kind, a pre-existing gap this pass also closed for the two functions it touched). **Not verified:** no live Supabase project in this environment — whether the migration applies cleanly, whether the partial index actually serves the approvals-page query efficiently at scale, and a real click-through of submit → notify → approve/reject → notify all need a manual pass before production use, same caveat category as every other feature built this session without live infrastructure to test against.

## 32. Manual Task Assignment — Person-to-Person Delegation (Third of the 11-Part Enterprise Spec)

Third area from the same 11-part spec, picked directly per the user's delegation. "Manual task assignment (person→person)" was flagged **Missing** in §2 — the only way a `daily_tasks` row ever came into existence was the AI generator, always assigning to the same person whose BSC data it was reasoning over.

**Reused rather than re-solved:** the underlying schema needed only one additive column, not a redesign — `daily_tasks` (`0006_performance_engine.sql`) already has no `NOT NULL` constraint on `user_id`/`position_id` and already supports a `task_date` distinct from `original_date`, so a manually-created row slots into the exact same table, the exact same "Today's Tasks" dashboard widget (`TaskList.tsx`), and the exact same self-rated completion flow (`updateTaskStatus`) an AI-generated one already uses — no parallel task system, no separate UI to maintain.

- **Assignment authority is `company_admin`/`manager`, assignable-to pool is `manager`/`staff`** — the identical reasoning already used for Score Approval (§31): this codebase has no org-chart-based "my direct reports" permission model (`reports_to_id` is only ever used for score-cascade math), so rather than invent one, this reuses the exact tenant-scoped `role in ('manager','staff')` query the scorecard's `responsible_person` picker (`teamOptions`) already runs — same people, same query shape, one more caller. `company_admin` and `manager` can both assign (a `manager`-only feature would be an odd gap given a `company_admin` already has broader authority everywhere else); `viewer` can neither assign nor receive, consistent with its read-only role everywhere else in the app.

## 33. KPI Score Governance Rework — Two-Level, Organizational-Hierarchy-Resolved Approval (Replaces §31)

Requested via a dedicated 33-section "MASTER DEVELOPMENT PROMPT" specifically about KPI score governance, delivered as a direct correction to what §31 shipped one turn earlier: approval must follow the organizational reporting hierarchy — immediate departmental manager first (non-final), then Head of Division/Division Chief (final, locks the score) — and `company_admin` must be excluded from approving unless they independently hold one of those positions. The spec explicitly asked for existing approval architecture to be inspected and extended rather than duplicated, which is what this section describes: §31's schema and Server Actions were reshaped in place, not replaced with a parallel system.

**The two clarifying questions this needed before any code was written** (asked via the tool, unanswered — proceeded on the stated recommended defaults per this session's "make the reasonable call, they'll redirect if needed" instruction, flagged here so the assumption is visible and correctable):

1. **"Division" does not exist as a schema concept.** A full-repo grep before writing any code confirmed it: `org_positions` has `office_department_name` and an optional `section_name`, and departments report up through generic `executive` positions (e.g. "Office of the COO") — there is no column, enum value, or code path representing a division distinct from a department. Rather than add new schema and rework the Org Setup wizard to let a `company_admin` formally designate divisions (a materially bigger change than the approval workflow itself), the final approver is resolved as **the nearest ancestor position of type `executive`** above the employee's immediate manager — the position that already functionally plays the division-head role in every org chart this template produces. `src/lib/approval-hierarchy.ts`'s `isDivisionLevel()` documents this mapping explicitly at the point it matters, not as a buried assumption.
2. **SLA/escalation integration (spec §28), formal time-boxed delegation (§18), and evidence-in-the-approval-view (§22) are deferred**, not built. SLA/Reminders/Escalation is already tracked as its own separate area in the 11-part enterprise spec (§2, still Missing) and working-day/holiday/timezone calendars are a substantial feature on their own; delegation (acting division head, start/end dates, audit trail) is real scope that deserves its own pass rather than a rushed add-on; evidence has nothing to hook into yet since KPI Evidence (also still Missing, §2) hasn't been built. None of the three block the core governance chain from working correctly today.

**Why §31's model had to change, not just gain a second approval step:** the org hierarchy, once actually traced through `reports_to_id`, doesn't give a fixed number of hops to "the division level" — it depends on whether a tenant's admin added an optional section layer and how many nested executive offices exist above a department. A naive "walk up two levels" rule would misroute in a large fraction of realistic org charts. `resolveApprovalChainFromPositions()` (`src/lib/approval-hierarchy.ts`) is written as a pure function over a flat position list specifically so this walk-and-classify logic could be unit-tested against the exact tree shapes `OrgWizard.tsx` actually produces (13 tests: normal 3-level and 4-level chains, a department with no section layer, a vacant manager/vacant division-head position, no executive ancestor at all, a cyclic `reports_to_id` chain, and the shallow-chain case where first and final approver collapse to the same person) — not asserted only against one happy-path fixture.

**Editor authority also moved off the `company_admin` role, for the specific field the spec covers.** `updateScorecardRow`'s `actual`-field edit is now owner-or-resolved-immediate-manager only (role-agnostic — a `company_admin` qualifies only by resolving as that position's occupant, never by their admin flag), while every *other* field on a `scorecard_rows` row (KPI definition, target, baseline, weights) remains `company_admin`-editable exactly as before — the spec's own framing separates *scorecard design* authority (which stays with `company_admin`) from *performance-score governance* (which doesn't). An unowned row (`responsible_person` null — no employee for the hierarchy to resolve against) is an explicitly stated carve-out: it stays `company_admin`-editable and auto-finalizes on edit, since there is no one to route it to.

**Self-approval and separation-of-duties, enforced at the point of use, not just documented:** `submitFirstApproval`/`submitFinalApproval` both reject if the calling user is the row's own `edited_by` — the person who entered or corrected the value can never be the one who signs off on it, at either level, regardless of whether they also happen to resolve as the approver (an edge case a broken or unusual org chart could otherwise produce). A single-manager chain (owner reports directly to an executive, so first and final approver resolve to the same person) is allowed rather than blocked — genuinely limited org charts exist — but is flagged via `chain.sameApprover` for a future audit-trail annotation; it is not silently treated as equivalent to a normal two-person chain.

**Locking is real, not a UI convention.** `updateScorecardRow` and `deleteScorecardRow` both hard-block once `approval_status = 'finally_approved'`, for every caller including `company_admin` — the only path back to an editable state is `requestAmendment()` → the row's own resolved final approver authorizes a `reopenScore()` → `reopened` (editable again, same rule as a correction) → a new edit restarts the two-level chain from `submitted`. There is deliberately no `company_admin` override on the reopen decision itself, consistent with keeping admin out of the approval chain; if a final-approver position goes vacant after a row is locked, the reopen path is genuinely stuck until the org chart is fixed — a known, stated limitation rather than a silently-added escape hatch that would undermine the whole point of this rework.

**What was built:** `supabase/migrations/0027_kpi_score_governance.sql` reshapes `scorecard_rows`' approval columns in place (`approval_status` becomes a 7-state enum: `not_submitted/submitted/first_approved/finally_approved/correction_required/amendment_requested/reopened`; old `pending_approval`/`approved`/`rejected` values are migrated forward, including carrying the old `approved_by`/`approved_at` onto the new `final_approved_by`/`final_approved_at` before dropping the old columns — pre-launch, so this reshapes rather than layers a compatibility shim) and adds a new `scorecard_row_versions` table (a real version history through the approval chain — distinct from `performance_snapshots`, which only ever recorded the raw actual-value text with no link to which approval cycle it belonged to). `src/lib/approval-hierarchy.ts` (new) — the pure resolver described above, plus `listPendingApprovalsForUser()` (also pure, reused so the approvals dashboard shows exactly what the API would accept, nothing more). `row-actions.ts` — `updateScorecardRow` reworked for the new authority/locking rules; `approveScorecardRow` replaced by `submitFirstApproval`/`submitFinalApproval`/`requestAmendment`/`reopenScore`. `notifications.ts` — the single-level `score_pending_review`/`score_approved`/`score_rejected` types replaced with seven new ones spanning both levels plus the "hierarchy not configured" case. `/dashboard/approvals` reworked into three sections (first-level, final, and amendment-reopen decisions) built from `listPendingApprovalsForUser`, no longer `company_admin`-gated — visible to every tenant member, since authority is positional now, not role-based; the nav link moved accordingly. `ScorecardTable.tsx`/`EditableCell.tsx` gained a fuller approval-state badge set, a lock indicator, and a new `RequestAmendmentControl.tsx` for locked rows.

**Verified:** `npx tsc --noEmit`, `npm run lint`, `npx vitest run` all clean — 264 tests, 33 net new (`approval-hierarchy.test.ts`, new, 14 tests against the pure resolver's exact tree shapes; `row-actions.test.ts`, fully rewritten, 29 tests covering every new action's authorization, self-approval, locking, and notification-routing behavior — the hierarchy resolver itself is mocked there since it already has its own dedicated, thorough test file). **Not verified:** no live Supabase project in this environment — the migration's `update`-then-`add constraint` sequencing, the RLS policy on the new `scorecard_row_versions` table, and a real end-to-end click-through (submit → first approval → final approval → lock → amendment → reopen) all need a manual pass before production use. **Explicitly out of scope, stated rather than silently dropped:** SLA/escalation, formal delegation, evidence integration (see the two clarifying-question defaults above); IP address/device/correlation-ID fields on `audit_log` (the spec's §20 asks for these — not added, since wiring them through would touch every existing `writeAuditLog()` call site across the codebase for marginal additional forensic value beyond what the new full row/version history already gives); and the "division" concept remains a pragmatic reuse of the existing `executive` position layer, not new schema — revisit if a tenant's real org structure genuinely needs departments grouped under a distinct division layer above the executive-office level.
